# P1 — WAL grows far beyond SQLite's default auto-checkpoint threshold under many concurrent shells

## Environment

- atuin 18.18.1 (Homebrew via Nix/home-manager)
- macOS 26.6.2
- Shell: zsh, `atuin init zsh --disable-up-arrow`, `auto_sync = false`

## Observed

`history.db` was 1.8 MB (3,640 history entries — a small dataset). `history.db-wal` had grown
to **23 MB, uncheckpointed** — 13× the size of the database itself.

Traced with `fs_usage` while triggering a single shell-hook invocation (one `cd`): **5,639
`pread` syscalls** against the WAL file for that one event. After manually running `PRAGMA
wal_checkpoint(TRUNCATE)` (which dropped the WAL to 0 bytes), the identical event cost
**1,071** syscalls — an 82% reduction, for what should be a near-instant operation on a
3,640-row table.

How this surfaced day to day: it presented as `mc` (Midnight Commander) being slow to change
directory. `mc`'s own panel navigation never touches a shell — but typing `cd` at its built-in
command line runs through a real background subshell, with the same `precmd`/`chpwd` hooks as
any interactive terminal. That subshell's atuin hook is what was paying the WAL-scan cost on
every single `cd`.

## What we found in `database.rs`

```rust
let opts = SqliteConnectOptions::from_str(...)
    .journal_mode(SqliteJournalMode::Wal)
    .optimize_on_close(true, None)
    .synchronous(SqliteSynchronous::Normal)
    ...

let pool = SqlitePoolOptions::new()
    .acquire_timeout(...)
    .connect_with(opts)
    .await?;
```

- No explicit `wal_autocheckpoint` pragma — relies on SQLite's compile-time default (~1000
  pages / ~4 MB), which the 23 MB WAL had clearly exceeded.
- `optimize_on_close` runs `PRAGMA optimize` (query-planner stats), not a WAL checkpoint —
  easy to mistake for one.
- Connection is a **pool** (`SqlitePoolOptions`), not a single long-lived connection. Since
  every shell's `precmd`/hook invocation spawns its own `atuin` process against the same
  database file, many concurrent short-lived connections from parallel terminal sessions
  seems like the most likely explanation for why the default auto-checkpoint doesn't keep
  this bounded — an overlapping reader from another session can prevent a `TRUNCATE`-level
  checkpoint from completing. We haven't proven that exact interleaving occurred, but it's
  consistent with everything observed and with how heavily this machine runs concurrent
  shells (dozens of parallel terminal/agent sessions is normal here).

## Workaround in place

An external hourly LaunchAgent runs `PRAGMA wal_checkpoint(TRUNCATE)` directly against the
database file, which is safe against a live database (SQLite's own locking governs it) and
resolves the slowdown. Not a real fix — just keeps the WAL from re-accumulating between
manual checks.

## Open question

Would it be worth atuin explicitly setting `wal_autocheckpoint` and/or issuing a periodic (or
shutdown-time) `wal_checkpoint(TRUNCATE)` itself, given the pool-of-short-lived-connections
access pattern this shell-hook design implies?

## Status

- [x] Root-caused locally, workaround deployed
- [x] Local fix implemented (uncommitted, this working tree): `checkpoint_wal_if_needed`
      in `crates/atuin-common/src/sqlite.rs`, wired into every client-side WAL store
      (`history.db`, record store, KV, scripts, AI sessions). `stat()`s the `-wal`
      sidecar on every pool-open; if it's over 16 MiB, runs a blocking
      `PRAGMA wal_checkpoint(TRUNCATE)`. Verified two ways: unit tests in
      `atuin-common` (temp-file-backed WAL db, threshold passed directly), and a manual
      sequential CLI repro (30 `history start`/`end` pairs, zero concurrency) showing
      unpatched WAL climbing unboundedly (2.39 MB, ~70 KB/pair, never shrinks even with
      a clean process-exit gap after every single command) versus patched staying flat
      at 32,992 bytes throughout. Confirms the root cause more precisely than
      originally framed above: PASSIVE checkpoints never shrink the WAL file on disk
      even when they fully succeed -- reader-overlap starvation makes it worse, but
      isn't actually required to reproduce unbounded growth.
